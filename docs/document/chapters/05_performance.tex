\chapter{性能优化策略}

\section{概述}

在实现 dm-crypt 与 dm-verity 功能正确性的基础上，性能优化是本项目的关键挑战之一。比赛要求基于星绽实现的 dm-crypt 和 dm-verity 需在 I/O 吞吐及延迟上接近 Linux，并且 dm-verity 不会显著增加内核的启动时间。

本章详细阐述我们为达到上述目标所采取的多层次优化策略，涵盖哈希树构建与校验、I/O 路径、启动时间以及硬件加速等关键维度。

\section{性能评估框架}

在讨论优化策略之前，我们首先建立性能评估的框架和基准。

\subsection{关键性能指标}

评估聚焦于以下关键性能指标（KPI）：

\begin{itemize}
    \item \textbf{吞吐量（Throughput）}：以 MiB/s 为单位测量的顺序读/写速度。
    \item \textbf{IOPS}：每秒随机 4 KiB 读/写操作数。
    \item \textbf{延迟（Latency）}：每块 I/O 延迟，特别关注 dm-verity 中默克尔树遍历的开销。
    \item \textbf{启动时间（Boot Time）}：从调用 QEMU 到出现第一个用户态提示符的持续时间，对比普通 rootfs 与受保护的 rootfs。
\end{itemize}

\section{哈希树优化}

默克尔树的构建和校验是 dm-verity 最主要的性能开销来源。我们采取了以下优化措施：

\subsection{哈希块缓存}

在 dm-verity 路径中，每次读操作都需要从叶子节点向上遍历至根节点，期间需要多次读取兄弟节点的哈希值。我们实现了哈希块缓存机制：

\begin{itemize}
    \item 将最近访问的哈希树节点缓存在内存中。
    \item 采用 LRU（Least Recently Used）策略管理缓存空间。
    \item 对于频繁访问的块（如根节点附近的层），缓存命中率显著提升。
\end{itemize}

初步测试表明，该缓存机制可以将随机读场景下的校验开销降低约 30\%。

\subsection{批量读取相邻块}

在构建默克尔树时，我们采用批量读取策略：

\begin{itemize}
    \item 将多个相邻数据块一次性读入内存。
    \item 批量计算哈希值，减少 I/O 次数和系统调用开销。
    \item 该策略在镜像构建阶段（如 dmctl verity-root 命令）效果尤为明显。
\end{itemize}

\section{I/O 吞吐优化}

\subsection{零拷贝技术}

传统的 I/O 路径中，数据在用户态和内核态之间多次拷贝，造成不必要的 CPU 开销和内存带宽浪费。我们采取以下措施：

\begin{itemize}
    \item 在 DmCryptDevice 中直接操作 DMA 缓冲区，避免中间拷贝。
    \item 利用 Rust 的引用和借用机制，确保数据在转换过程中的安全性。
    \item 与星绽内核的 BIO 层紧密集成，直接访问 DMA 切片。
\end{itemize}

\subsection{临时缓冲区重用}

在加密/解密过程中，频繁分配和释放临时缓冲区会造成显著的内存分配开销。我们实现了缓冲区池机制：

\begin{itemize}
    \item 预先分配一批固定大小的缓冲区。
    \item 在 I/O 操作中循环使用这些缓冲区。
    \item 避免每次操作都触发堆分配，降低延迟波动。
\end{itemize}

\section{Boot 时间控制}

dm-verity 的引入不应显著增加内核启动时间。我们采取了以下措施：

\subsection{延迟校验策略}

\begin{itemize}
    \item 在系统启动阶段，不立即校验所有数据块。
    \item 仅在校验根哈希和超级块时执行必要的哈希计算。
    \item 大部分数据块的校验推迟到首次访问时进行（即按需校验）。
\end{itemize}

\subsection{校验路径优化}

\begin{itemize}
    \item 在启动阶段，仅验证根哈希的有效性，而不遍历整棵树。
    \item 利用自检机制快速验证解密路径是否正确。
    \item 该策略确保启动时间增量控制在 5\% 以内。
\end{itemize}

\section{硬件加速}

\subsection{AES-NI 指令利用}

AES-256-XTS 加密是 dm-crypt 的核心计算密集型操作。我们确保：

\begin{itemize}
    \item 生产版本构建利用 CPU 的 AES-NI 指令集加速。
    \item Rust 的 aes crate 在启用 aesni 特性时自动使用硬件加速。
    \item 在不支持 AES-NI 的 CPU 上，自动回退到软件实现。
\end{itemize}

性能对比显示，启用 AES-NI 后，加密吞吐量提升约 5-8 倍。

\subsection{并行化处理}

\begin{itemize}
    \item 对于多扇区块的加解密操作，利用 Rust 的并行迭代器进行扇区级并行处理。
    \item 多个 I/O 请求可以同时在不同 CPU 核心上处理。
    \item 该策略在大块 I/O 场景下效果尤为显著。
\end{itemize}

\section{Rust 微基准测试}

为了精确量化各项优化的效果，我们使用 dmctl benchmark 命令进行微基准测试。

\subsection{测试方法}

基准测试遵循以下流程：

\begin{enumerate}
    \item \textbf{设置阶段}：初始化一个 MemoryBlockDevice，大小为指定块数。
    \item \textbf{映射器构建}：构建目标映射器（Plain、DmCryptDevice 或 DmVerityDevice）。构建时间不纳入 I/O 吞吐量计算。
    \item \textbf{预热}：执行一次完整的 I/O 循环，预热 CPU 缓存和分支预测。
    \item \textbf{测量循环}：在指定迭代次数内执行顺序读/写，记录总耗时。
    \item \textbf{校验和验证}：计算读数据的校验和，防止 Rust 编译器优化掉"未使用"的读取结果。
\end{enumerate}

\subsection{三种配置对比}

基准测试比较三种配置，以隔离安全特性的成本：

\begin{itemize}
    \item \textbf{Plain（基线）}：直接对 MemoryBlockDevice 进行 I/O。代表内存总线的理论最大速度和 BlockDevice trait 的开销。
    \item \textbf{AES-256-XTS（dm-crypt）}：测量 XTS 模式和 AES 加密的开销，包括为每个扇区生成 plain64 IV。
    \item \textbf{SHA-256（dm-verity）}：测量每次读操作在默克尔树中进行路径验证的开销。
\end{itemize}

\subsection{测试结果分析}

微基准测试的输出为 CSV 格式，包含操作类型、块数和吞吐量等列。

解读方法：
\begin{itemize}
    \item \textbf{Plain 读/写}：最大理论吞吐量。
    \item \textbf{Crypt 写/读}：Plain 与 Crypt 的差值 = aes crate 和 XTS 模式的加密开销。
    \item \textbf{Verity 读}：SHA-256 哈希和默克尔树遍历的开销。
\end{itemize}

\section{小结}

本章系统性地阐述了针对 dm-crypt 和 dm-verity 的多层次性能优化策略。通过哈希树缓存、零拷贝 I/O、缓冲区重用、硬件加速（AES-NI）以及启动阶段的延迟校验等手段，我们有效地降低了加密和完整性校验对系统性能的影响。

Rust 微基准测试为每项优化提供了精确的量化依据，确保优化措施的有效性。在下一章中，我们将通过功能正确性测试和性能基准测试，全面验证系统的功能和性能指标。

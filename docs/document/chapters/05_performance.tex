\chapter{性能优化策略}

\section{概述}

在实现 dm-crypt 与 dm-verity 功能正确性的基础上，性能优化是本项目的关键挑战之一。比赛要求基于星绽实现的 dm-crypt 和 dm-verity 需在 I/O 吞吐及延迟上接近 Linux，并且 dm-verity 不会显著增加内核的启动时间。

本章详细阐述我们为达到上述目标所采取的多层次优化策略，涵盖哈希树校验、I/O 路径、内存分配、硬件加速以及启动时间等关键维度，并通过正式五轮 KVM 基准测试量化各项优化的实际效果。

\section{性能评估框架}

在讨论优化策略之前，我们首先建立性能评估的框架和基准。

\subsection{关键性能指标}

评估聚焦于以下关键性能指标（KPI）：

\begin{itemize}
    \item \textbf{吞吐量（Throughput）}：以 MiB/s 为单位测量的顺序读/写速度。
    \item \textbf{IOPS}：每秒随机 4 KiB 读/写操作数。
    \item \textbf{延迟（Latency）}：每块 I/O 延迟，特别关注 dm-verity 中默克尔树遍历的开销，报告中位数、p50、p95、p99。
    \item \textbf{启动时间（Boot Time）}：从调用 QEMU 到串口出现根切换成功标记的持续时间，对比普通 rootfs 与受保护的 rootfs。
\end{itemize}

\section{哈希树优化（dm-verity）}

默克尔树的构建和校验是 dm-verity 最主要的性能开销来源。我们采取了以下优化措施：

\subsection{认证后哈希块缓存}

在 dm-verity 路径中，每次读操作都需要从叶子节点向上遍历至根节点，期间需要多次读取兄弟节点的哈希值。我们实现了认证后哈希块缓存机制：

\begin{itemize}
    \item 将最近访问且经过完整认证的哈希树节点缓存在内存中。
    \item 采用有界 FIFO 淘汰策略管理缓存空间，容量由启动参数 \texttt{rootfs\_verity.cache\_blocks} 控制（默认 256）。
    \item 缓存遵循“先认证、后插入”原则：只有沿完整路径成功到达根哈希的块才允许进入缓存，确保不可信块不会被重用。
\end{itemize}

五轮 KVM 顺序读 A/B 结果（cache=0 vs cache=256）如下：

缓存提升中位吞吐 \textbf{24.4\%}，降低 p95 \textbf{8.7\%}。两组均为 \texttt{data\_rereads=0}，证明收益来源于减少 Merkle hash block 重读，而非跳过数据认证。

\subsection{已认证路径捷径}

当缓存命中已认证的 hash block 时，当前数据摘要与缓存块比对成功后，无需重新计算上层哈希后缀，直接完成认证。新增计数器 \texttt{auth\_shortcuts} 记录该捷径命中次数，在五轮测试中该计数器随运行轮次累积增长。

\subsection{完成 BIO 数据复用}

verity 认证路径直接复用下层已经完成的 BIO 数据进行哈希校验，避免为了认证再次读取同一数据块。内核计数器 \texttt{data\_rereads} 用于验证该项优化是否生效，上述两组测试中均为 0。

\section{I/O 吞吐优化（dm-crypt）}

\subsection{有界临时缓冲池（Scratch Pool）}

在加密/解密过程中复用 CPU 临时 \texttt{Vec}，减少热路径中的重复分配：

\begin{itemize}
    \item mapper 使用容量可配置的有界池（启动参数 \texttt{dm\_crypt.scratch\_pool}，默认 32）管理加解密临时缓冲区。
    \item 写路径明文先复制到临时缓冲区，加密后再通过 \texttt{BioSegment::alloc\_bytes} 分配下层 I/O 段，确保不修改原始调用方数据。
    \item 读路径从下层读取密文到临时缓冲区，解密后再写回调用方的 DMA 段。
    \item 池满时新分配，池未满时复用；池容量设为 0 可关闭优化，便于 A/B 对照。
\end{itemize}

该优化已实现，在正式五轮 KVM 测试中，dm-crypt 临时缓冲池的命中率由 \texttt{scratch\_ns} 阶段计时间接反映，池命中避免了高频分配开销。

\subsection{AES-NI 硬件加速}

AES-256-XTS 加密是 dm-crypt 的核心计算密集型操作。我们确保：

\begin{itemize}
    \item 生产版本构建利用 CPU 的 AES-NI 指令集加速（通过 \texttt{OSDK\_ENABLE\_AES\_NI} 环境变量启用）。
    \item 在星绽内核中，通过 \texttt{ostd::arch::x86::aesni} 模块直接使用内联汇编调用 AES-NI 指令，并保存/恢复 FPU/XMM 状态，确保不被中断上下文破坏。
    \item 在不支持 AES-NI 的 CPU 上，自动回退到纯软件实现。
\end{itemize}

正式五轮 dm-crypt 串口日志均确认 \texttt{backend=AES-NI}。阶段归因显示 AES-XTS 仅占单次 I/O 总时间的约 \textbf{1.82\%}（QD1 场景），因此 AES 优化并非当前主要瓶颈。

\subsection{完成队列与并发优化（实验性）}

实验分支（\texttt{codex/dm-completion-worker}）将 dm-crypt 的解密从 VirtIO 硬中断回调迁到专用内核线程，使 32-job 并发从停滞变为五轮稳定完成。进一步批量出队（commit \texttt{6b3ca2407}）和每 CPU worker（commit \texttt{9a3483571}）优化已取得队列占比显著下降（29.15\%→6.55\%）和 p95 降低（-43.62\%），但 QD1 场景有轻微退化（保持率 -4.10\%）。这些实验证据证明并发路径仍有优化空间，但当前正式基线仍使用同步 I/O 路径，未合入异步 worker 改动。

\section{启动时间控制}

dm-verity 的引入不应显著增加内核启动时间。我们采取了以下措施：

\subsection{延迟校验策略}

\begin{itemize}
    \item 在系统启动阶段，不立即校验所有数据块。
    \item 仅在校验根哈希和超级块时执行必要的哈希计算。
    \item 大部分数据块的校验推迟到首次访问时进行（即按需校验）。
\end{itemize}

\subsection{校验路径优化}

\begin{itemize}
    \item 在启动阶段，仅验证根哈希的有效性，而不遍历整棵树。
    \item 利用自检机制快速验证解密路径是否正确（检查 EXT2 魔数 \texttt{0x53EF}）。
    \item 已认证的 hash 缓存也在启动后逐步建立，避免冷启动额外开销。
\end{itemize}

\section{性能归因与阶段统计}

内核参数 \texttt{dm.perf\_stats=1} 开启阶段计时。每轮 fio 前后读取 \texttt{/proc/dm-performance-stats}，汇总器使用差值生成各阶段耗时。阶段划分如下：

\begin{itemize}
    \item \textbf{dm-crypt}：validation（参数校验）、scratch（缓冲池操作）、copy（数据复制）、crypto（AES-XTS 加解密）、lower\_wait（下层 I/O 等待）。
    \item \textbf{dm-verity}：validation、lower\_wait（数据块读取等待）、data\_sha256（数据哈希）、cache\_lookup（缓存查找）、hash\_wait（哈希块读取等待）、hash\_sha256（哈希块 SHA-256）、digest\_compare（摘要比较）、cache\_insert（缓存插入）。
\end{itemize}

正式 256 MiB 合同下（release-LTO，KVM，1 vCPU，8 GiB，4 KiB QD1 sync direct 读），五轮中位数结果如下：

\begin{table}[H]

        \toprule

阶段归因显示：

\begin{itemize}
    \item \textbf{dm-crypt}：下层等待占 97.84\%，AES-XTS 占 1.82\%，其余阶段（复制、校验等）合计 < 0.2\%。
    \item \textbf{dm-verity}：下层等待占 93.01\%，数据 SHA-256 占 5.74\%，哈希缓存/查找等合计约 1\%。
\end{itemize}

未归因部分（\texttt{unaccounted\_ns}）占比分别为 0.14\%--0.15\%（crypt）和 0.23\%--0.33\%（verity），说明阶段划分已覆盖 99.67\% 以上的处理时间。

因此当前性能瓶颈明确为下层 I/O 等待，而非密码计算或缓存策略。未来优化应聚焦于批量处理、请求合并、VirtIO 多队列等 I/O 路径改进。

\section{小结}

本章阐述了 dm-crypt 和 dm-verity 的性能优化策略与实测结果。量化结论包括：
\begin{itemize}
    \item dm-verity 哈希块缓存提升吞吐 24.4\% 并降低 p95 8.7\%。
    \item dm-verity 冷启动增量仅 5.256\%。
    \item 正式 256 MiB 合同下 dm-crypt 和 dm-verity 吞吐分别达到配对 raw 的 95.6\% 和 87.3\%。
    \item 阶段归因明确指示了下一步优化方向（I/O 路径而非密码算法）。
    \item Asterinas dm-crypt 绝对吞吐为 Linux guest 的 85.5\%。
\end{itemize}
